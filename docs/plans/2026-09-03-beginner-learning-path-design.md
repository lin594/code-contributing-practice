# 面向大一新生的 Git/GitHub 学习路径设计

## 目标与边界

本仓库要成为一条可以独立完成的学习路径：学生只需要 GitHub 账号、电脑和本仓库链接，就能从“Git 与 GitHub 是什么”走到能够参与一次规范的团队协作。主路径使用 Git 命令行和 GitHub 网页，因为这套组合最容易迁移到课程项目和开源仓库；GitHub Desktop 只提供操作对照。课程不讲 Git 内部对象、复杂历史修复、发布流程或项目管理功能。

成功标准不是“读完文档”，而是学生在真实 GitHub Fork 中完成 Issue、分支、commit、push、Pull Request、Draft、Review、上游同步和冲突解决，并能从自动反馈中自行恢复常见错误。

## 方案选择

考虑过三种结构：

1. 保留四个大练习，只扩写说明。实现最小，但 Fork/PR、提交历史、Review、冲突之间的跨度仍然存在。
2. 建立八个递进的自动练习。每关只新增一个主要概念，同时保留真实 GitHub 交互。这是采用的方案。
3. 建立十二个以上的微练习。颗粒度最细，但学生会反复创建 Issue、分支和 PR，机械操作会盖过概念学习，维护成本也明显上升。

八关之外设置“准备篇”，负责安装、配置、认证、终端基础和心智模型；设置“毕业后实战”，指导学生把同一流程迁移到课程小组或真实开源项目。

## 学习路径

每一课固定采用“目标 → 概念 → 预测 → 实操 → 自查 → 常见错误 → 复盘”的结构。学生知道为什么执行命令、执行后应观察什么，而不是复制一串无法解释的命令。

| 阶段 | 新概念 | 可验证产出 |
| --- | --- | --- |
| 准备篇 | Git/GitHub 区别、终端、身份与认证、三区模型 | 本地环境自检通过 |
| 1 第一次 PR | Fork、clone、origin/upstream、branch、commit、push、PR | 一条 commit 的真实 PR |
| 2 原子提交 | working tree、staging area、两次独立提交 | 恰好两条线性 commit |
| 3 清晰协作 | 分支名、Issue 关联、PR 标题与说明 | 可供陌生人理解的 PR |
| 4 Draft | 工作中与可评审状态的区别 | 先 Draft、后 Ready for review |
| 5 Review | 在原 PR 继续修改和回复 | 新 commit 与回复记录 |
| 6 同步上游 | fetch、merge/rebase、远端跟踪分支 | 纳入无冲突上游更新 |
| 7 冲突 | 冲突原因、标记、取舍与中止 | 保留双方意图的解决结果 |
| 8 综合协作 | 把沟通、Review、同步组合起来 | 一次完整的模拟团队协作 |

关卡严格按顺序解锁，但每关创建独立的临时上游分支，避免前一关错误污染下一关。每关预计 10–30 分钟，学生可以分多次完成；10 天提醒、14 天过期。

## 自动化架构

课程继续使用 Issue Form 创建会话。机器人从可信的默认分支创建 `practice/ex<关卡>/issue-<编号>-<用户名>`，写入只读的 `session.json` 和可编辑的 `workspace.md`。学生从该分支建立自己 Fork 中的 topic branch，并把 PR 指向临时 base。通过后机器人 squash merge、关闭 Issue、删除临时分支，因此 `main` 不保存学员产物。

自动检查分为三层：所有关卡共享身份、会话、base、文件范围和自动合并安全检查；关卡规则验证本课的新技能；分支名、标题、commit message 等习惯先作为建议出现，在对应课程讲过后才成为必须项。第 4 关记录是否见过 Draft 状态，第 5/8 关记录首次 Review 对应的 head SHA，第 6/7/8 关记录机器人写入的上游 commit，并通过祖先关系验证学生确实同步过，而不是只改出相同文字。

课程升级为会话 schema v2，并提供显式的旧会话清理操作。高权限 `pull_request_target` 工作流始终只运行默认分支代码；Fork 内容只作为数据读取，自动合并前重新验证 exact head SHA。

## 反馈、错误恢复与验证

失败反馈必须回答三件事：发生了什么、为什么不符合本课目标、下一条安全命令或网页操作是什么。每个失败项使用稳定规则 ID，反馈评论原位更新，学生不需要在多条机器人评论间寻找最新状态。文档中的排错入口按“我现在看到的现象”组织，危险恢复命令不作为首选方案；历史重写只允许在个人 topic branch 使用 `--force-with-lease`。

自动化使用 Node 内置测试框架覆盖 1–8 关的通过样例、各关关键失败样例、Draft/Review 状态、上游提交注入资格、会话解析和安全边界。文档验收包括内部链接、关卡编号、命令占位符和从 README 到第一关的完整人工走查。发布前维护者必须用独立测试账号分别走通 merge 和 rebase 路径，并确认普通维护 PR 永远不会触发练习自动合并。
